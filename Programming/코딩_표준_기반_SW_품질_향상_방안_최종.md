# 코딩 표준 기반 SW 품질 향상 방안

## 1. 목적

본 코딩 표준의 목적은 단순히 코드의 형식을 통일하는 데 있지 않다. 핵심은
개발자가 실수하기 어려운 구조를 만들고, 문제가 발생했을 때 원인을 빠르게
찾을 수 있으며, 다른 개발자가 코드를 읽고 수정할 때 잘못된 추론을 하지
않도록 하는 것이다.

본 표준은 가독성을 최우선으로 두고 있으며, 코드 자체가 가능한 한 문서의
역할을 하도록 하는 방향을 기본 원칙으로 삼는다.

특히 다음 원칙들은 SW 품질 향상과 직접적으로 연결된다.

- `null` 사용을 최소화하고, 필요한 경우 코드에서 명시적으로 드러낸다.
- 외부에서 들어오는 데이터는 시스템 경계에서 검증한다.
- 외부와의 경계에서 발생할 수 있는 예외는 해당 경계에서 처리한다.
- 경계를 통과한 내부 데이터는 유효하다고 가정한다.
- 내부에서 발생하는 비정상 상태와 예외는 정상적인 오류 흐름이 아니라
  버그로 간주한다.
- 내부의 설계 가정과 불변조건은 `Debug.Assert()`를 적극 사용하여 개발
  단계에서 조기에 발견한다.
- 코드의 길이를 줄이는 것보다 실행 흐름과 의도를 명확하게 표현하는 것을
  우선한다.

이러한 규칙들은 각각 독립적인 스타일 규칙이 아니라, 외부의 불확실성이
프로그램 내부로 확산되는 것을 막고 내부 코드의 상태를 단순하고 예측
가능하게 유지하기 위한 하나의 품질 관리 전략이다.

## 2. Null을 적극적으로 관리해야 하는 이유

`null` 자체가 항상 나쁜 것은 아니다. 문제는 어떤 값이 `null`일 수 있는지
개발자가 명확하게 알 수 없는 상태이다.

다음과 같은 함수가 있다고 가정한다.

``` csharp
User GetUser(int _userID);
```

호출하는 개발자는 함수 이름과 반환형을 보고 정상적으로 호출되면 `User`
객체가 반환된다고 생각하기 쉽다.

그런데 실제 구현에서 사용자가 없을 때 `null`을 반환한다면 다음과 같은
코드가 자연스럽게 만들어질 수 있다.

``` csharp
User user = GetUser(_userID);
PrintUserName(user.Name);
```

이 경우 문제는 단순히 `NullReferenceException`이 발생한다는 것만이
아니다. 실제 잘못된 결정은 `GetUser()`의 반환값을 처리하지 않은 지점에서
발생했지만, 오류는 훨씬 뒤의 `user.Name` 접근에서 나타날 수 있다.

``` text
문제의 원인
    ↓
GetUser()의 반환 계약을 잘못 이해

실제 오류 발생
    ↓
user.Name 접근
```

즉, 오류의 원인과 오류가 드러나는 위치가 멀어진다. 이것은 장애 분석과
디버깅 비용을 증가시킨다.

본 표준은 이를 줄이기 위해 함수의 매개변수로 `null`을 허용하지 않는 것을
추구하고, 함수에서도 가능한 한 `null`을 반환하지 않도록 한다. 불가피하게
`null`을 허용하는 경우에는 매개변수나 함수 이름에 `OrNull`을 붙여 그
사실을 명시하도록 한다.

``` csharp
User GetUserOrNull(int _userID);
void SetUser(User _userOrNull);
```

이렇게 하면 함수 내부를 확인하지 않아도 호출자가 계약을 알 수 있다.

``` text
GetUser()
→ 성공적으로 반환되었다면 User가 존재해야 함

GetUserOrNull()
→ User가 존재하지 않을 수도 있음
```

여기에 Nullable Reference Types를 함께 사용하면 더 강한 효과를 얻을 수
있다.

``` csharp
User? GetUserOrNull(int _userID);
```

역할은 다음과 같이 나뉜다.

``` text
OrNull
→ 사람에게 null 가능성을 전달

?
→ 컴파일러에게 null 가능성을 전달
```

즉 `OrNull`은 API 가독성을 높이고, Nullable Reference Types는 컴파일러가
실수를 검출하도록 한다.

> **Null 관리의 목적**  
> Null을 완전히 없애는 것이 아니라, **Null이 존재할 수 있는 위치를
> 제한하고 그 가능성을 명확하게 표현하는 것**이다.

이를 통해 다음과 같은 품질 향상을 기대할 수 있다.

- 예상하지 못한 `NullReferenceException` 감소
- 입력과 반환값의 계약 명확화
- 코드 리뷰 시 `null` 가능성 확인 용이
- 함수 내부를 보지 않고도 올바른 호출 방법 판단 가능
- 오류 발생 위치와 실제 원인 사이의 거리 감소

## 3. 외부 데이터는 경계에서 검증해야 하는 이유

프로그램 외부에서 들어오는 데이터는 기본적으로 신뢰할 수 없다. 여기서
외부란 인터넷이나 사용자 입력만 의미하지 않는다.

다음과 같은 대상도 모두 프로그램 내부의 관점에서는 외부가 될 수 있다.

- 사용자 입력
- 파일
- 설정 파일
- 네트워크 패킷
- TCP / UDP 데이터
- Serial 통신
- 센서 데이터
- 외부 장비
- DB
- 외부 DLL
- 외부 API
- 다른 프로세스

이러한 데이터는 프로그램이 직접 통제할 수 없는 상태에서 생성된다. 따라서
값이 잘못되거나, 예상한 범위를 벗어나거나, 데이터가 누락되거나, 통신
자체가 실패할 가능성이 있다.

본 표준은 이런 데이터를 외부와 내부의 경계가 바뀌는 지점에서 검증하고,
유효하지 않은 데이터는 내부 함수에 전달하지 않는 것을 원칙으로 한다.
경계를 통과한 이후의 내부 데이터는 유효하다고 가정한다.

예를 들어:

``` csharp
public void ReceivePacket(byte[] _data)
{
    if (_data == null)
    {
        return;
    }

    if (_data.Length < MIN_PACKET_SIZE)
    {
        return;
    }

    if (!IsValidHeader(_data))
    {
        return;
    }

    ProcessPacket(_data);
}
```

외부에서 들어온 데이터는 이 지점에서 충분히 검사한다. 그리고 내부
함수에서는:

``` csharp
private void ProcessPacket(byte[] _data)
{
    Debug.Assert(_data != null);
    Debug.Assert(_data.Length >= MIN_PACKET_SIZE);

    ...
}
```

처럼 사용할 수 있다.

이 구조의 핵심은 **검사를 하지 않는 것이 아니라 검사의 위치를 정하는
것**이다.

만약 모든 내부 함수가 각각 방어 코드를 가진다면:

``` csharp
private void ProcessPacket(Packet _packet)
{
    if (_packet == null)
    {
        return;
    }

    ...
}

private void DecodePacket(Packet _packet)
{
    if (_packet == null)
    {
        return;
    }

    ...
}

private void ApplyPacket(Packet _packet)
{
    if (_packet == null)
    {
        return;
    }

    ...
}
```

코드는 겉보기에는 안전해 보일 수 있다. 하지만 실제로는 다음 문제가
발생한다.

- 어디까지 검증된 데이터인지 알기 어렵다.
- 동일한 검증이 여러 곳에서 반복된다.
- 검증 기준이 함수마다 달라질 수 있다.
- 핵심 처리 코드보다 방어 코드가 더 많아진다.
- 잘못된 데이터가 어디에서 최초로 들어왔는지 찾기 어려워진다.
- 내부에서 잘못된 상태가 발생해도 조용히 `return`되어 버그가 숨을 수
  있다.

따라서 역할을 명확하게 나눈다.

``` text
외부 영역
→ 신뢰하지 않음

Boundary
→ 검증 / 거부 / 외부 오류 처리

내부 영역
→ 검증된 데이터라는 계약을 신뢰
```

Boundary Validation은 단순한 입력 검사 규칙이 아니다. **검증 책임을
한정하여 내부 코드의 상태 공간과 복잡도를 줄이는 설계 원칙**이다.

## 4. 예외는 경계에서 처리해야 하는 이유

본 코딩 표준에서 말하는 "예외는 경계에서 처리한다"는 의미를 정확하게
이해하는 것이 중요하다.

이 원칙은 다음을 의미하지 않는다.

> 내부에서 발생한 예외를 계속 상위 계층으로 전달한 뒤 마지막 경계에서
> 한꺼번에 처리한다.

본 표준에서는 외부 데이터의 유효성을 경계에서 검증하고, 내부 함수에서는
예외를 던지지 않도록 노력하며, 예외는 경계에서 처리하는 것을 원칙으로
한다.

따라서 의도는 다음과 같다.

> **외부 환경 때문에 정상적으로 발생할 수 있는 실패는 외부와 접하는
> 경계에서 처리하고, 프로그램 내부에서는 예외가 정상적인 제어 흐름으로
> 발생하지 않는 구조를 만든다.**

예를 들어 다음은 외부와의 경계다.

- 파일 읽기
- 네트워크 통신
- Serial 통신
- 외부 장비 API
- DB 접근
- 외부 DLL
- 사용자 입력 처리
- 설정 파일 로딩

이 영역에서는 프로그램이 통제할 수 없는 이유로 실패할 수 있다.

``` csharp
public void ReceiveData()
{
    try
    {
        byte[] data = mTransport.Read();

        if (!IsValidPacket(data))
        {
            return;
        }

        ProcessPacket(data);
    }
    catch (IOException _exception)
    {
        LogCommunicationError(_exception);
        HandleCommunicationFailure();
    }
}
```

여기에서 발생하는 `IOException`은 반드시 프로그램 버그라고 볼 수 없다.
예를 들면 다음과 같은 상황은 정상적인 실행 환경에서도 발생할 수 있다.

- 장비 연결 해제
- 통신 단절
- 파일 삭제
- 권한 문제
- 외부 장비 응답 실패

이러한 오류는 외부 세계와 접촉하는 경계에서 예상 가능한 실패로 처리한다.

반면 경계를 통과한 내부 코드는 다르게 본다.

``` csharp
private void ProcessPacket(byte[] _data)
{
    Debug.Assert(_data != null);
    Debug.Assert(_data.Length >= MIN_PACKET_SIZE);

    ...
}
```

이 함수에 `null`이 들어오거나 규격보다 짧은 패킷이 들어왔다면, 외부
환경이 잘못된 것이 아니라 외부 데이터를 검증해야 했던 코드 또는 내부
호출 구조가 잘못된 것이다.

따라서 내부에서 발생하는 다음과 같은 문제는 일반적으로 정상적인 오류가
아니라 버그로 본다.

- `NullReferenceException`
- `IndexOutOfRangeException`
- 경계를 통과한 이후 발견된 잘못된 데이터
- 초기화되어 있어야 하는 객체가 초기화되지 않은 상태
- 내부 상태 머신에서 존재해서는 안 되는 상태
- 처리되어야 하는 enum 값이 누락된 경우
- 잘못된 내부 인덱스
- 깨진 invariant

이런 문제를 다음처럼 처리해서는 안 된다.

``` csharp
private void ProcessPacket(byte[] _data)
{
    try
    {
        ...
    }
    catch
    {
        return;
    }
}
```

이 코드는 프로그램을 당장 계속 실행시킬 수는 있지만, 실제로는 버그를
해결한 것이 아니라 숨긴 것이다. 잘못된 상태가 그대로 남아 다른 데이터를
오염시키거나, 더 먼 위치에서 전혀 다른 형태의 장애를 만들 수도 있다.

따라서 내부 오류에 대한 기본 원칙은:

``` text
내부 예외 발생
    ↓
정상적인 상황으로 취급하지 않음
    ↓
원인 조사
    ↓
버그 수정
```

이어야 한다.

본 표준에서는 enum `switch`의 `default:`처럼 개발자가 처리해야 하는
경우를 빠뜨렸는지 발견하기 위한 특수한 상황에서는 예외 발생을 허용한다.
이는 일반적인 오류 복구 목적이 아니라 프로그래밍 오류를 적극적으로
드러내기 위한 장치다.

따라서 예외 정책은 다음과 같이 정리할 수 있다.

``` text
외부에서 발생 가능한 실패
→ Boundary에서 처리

내부에서 발생한 예외
→ 버그로 간주하고 원인 수정

내부에서 존재해서는 안 되는 상태
→ Assert / Debug.Fail 등을 통해 조기에 발견

일부 특수한 프로그래밍 오류
→ 의도적으로 예외를 발생시켜 누락된 처리를 발견
```

이 구조의 장점은 프로그램 내부에서 **어디까지가 정상적으로 발생할 수
있는 실패인가**가 명확해진다는 것이다.

## 5. Debug.Assert를 강하게 사용해야 하는 이유

`Debug.Assert()`는 외부 입력 검증을 대신하는 기능이 아니다. 두 기능의
목적은 명확히 다르다.

``` text
Validation
→ 실제 사용 환경에서 정상적으로 발생할 수 있는 잘못된 외부 입력을 처리

Debug.Assert
→ 프로그램 설계상 발생해서는 안 되는 내부 상태를 발견
```

본 코딩 표준은 코드를 작성하면서 세운 가정에 `Debug.Assert()`를
사용하도록 하고 있으며, 실행될 일이 없다고 판단되는
`switch default:`에는 `Debug.Fail()`을 사용하도록 한다.

예를 들어:

``` csharp
private void ProcessPacket(Packet _packet)
{
    Debug.Assert(_packet != null);

    ...
}
```

이 코드는 다음과 같은 뜻이 아니다.

> `_packet`이 `null`이면 안전하게 `return`하자.

의미는 다음과 같다.

> **이 함수에 들어오는 시점에는 `_packet`이 반드시 존재해야 한다. 만약
> `null`이라면 프로그램 내부의 계약이 깨진 것이다.**

이 차이가 중요하다.

잘못된 내부 상태에 대해 다음처럼 작성하면:

``` csharp
if (_packet == null)
{
    return;
}
```

프로그램은 조용히 계속 실행된다. 하지만 개발자는 다음을 알기 어렵다.

- 왜 `null`이 들어왔는가?
- 어디에서 처음 잘못되었는가?
- 이 상태에서 `return`해도 전체 시스템이 정상인가?
- 이후 상태는 여전히 유효한가?

오히려 버그를 숨길 수 있다.

반면:

``` csharp
Debug.Assert(_packet != null);
```

을 사용하면 개발 과정에서 설계상 존재해서는 안 되는 상태가 발생한 즉시
알 수 있다.

### Assert가 없을 때

``` text
잘못된 상태 발생
    ↓
계속 실행
    ↓
다른 상태 또는 데이터 변경
    ↓
몇 단계 더 실행
    ↓
다른 위치에서 Exception
    ↓
실제 원인 추적 필요
```

### Assert를 사용할 때

``` text
잘못된 상태 발생
    ↓
Assert 실패
    ↓
계약이 깨진 위치에서 즉시 발견
```

따라서 Assert의 가장 큰 목적은 **버그를 최초 원인에 가까운 위치에서
발견하는 것**이다.

예를 들어 다음과 같은 조건은 Assert 사용 후보가 될 수 있다.

``` csharp
Debug.Assert(mDevice != null);
Debug.Assert(_packet.Length >= HEADER_SIZE);
Debug.Assert(_index >= 0);
Debug.Assert(_index < mItems.Count);
Debug.Assert(mState == EState.Ready);
Debug.Assert(mTransport.IsConnected);
Debug.Assert(mCurrentFrame != null);
```

이런 코드들은 함수나 클래스의 중요한 전제조건을 표현한다.

주석으로:

``` csharp
// 여기에서는 반드시 Ready 상태여야 한다.
```

라고 쓰는 것보다:

``` csharp
Debug.Assert(mState == EState.Ready);
```

라고 작성하는 것이 더 강력하다.

주석은 오래되어 실제 코드와 달라져도 아무 일도 일어나지 않는다. 하지만
Assert는 프로그램 실행 중 실제 가정과 코드가 일치하는지 확인한다.

따라서 `Debug.Assert()`는 단순한 디버깅 편의 기능이 아니라 **실행 가능한
설계 문서**의 역할도 한다.

------------------------------------------------------------------------

## 6. Boundary Validation과 Assert는 서로 반대되는 개념이 아니다

처음 보면 다음 두 규칙은 서로 모순되는 것처럼 보일 수 있다.

> "입력값을 적극적으로 검사한다."
>
> "내부에서는 값을 믿고 Assert를 사용한다."

하지만 검사 대상이 다르다.

### 외부 경계

외부 데이터는 잘못될 수 있다. 따라서:

``` csharp
if (!IsValidPacket(_data))
{
    return;
}
```

처럼 실제 실행 환경에서도 처리해야 한다.

### 내부 코드

Boundary를 통과한 값은 이미 검증되었다고 계약한다. 따라서:

``` csharp
Debug.Assert(IsValidPacket(_data));
```

처럼 계약이 실제로 유지되고 있는지 확인한다.

즉 동일한 조건이 상황에 따라 다음과 같이 달라질 수 있다.

``` text
Boundary
    ↓
if 검사
    ↓
잘못된 값은 정상적으로 거부

Internal
    ↓
Debug.Assert
    ↓
같은 조건이 깨지면 버그
```

이렇게 하면 외부 입력은 안전하게 처리하면서도 내부 코드에 반복적인 방어
코드를 넣지 않아도 된다.

------------------------------------------------------------------------

## 7. Null 관리, Boundary, Exception, Assert는 하나의 품질 체계다

이 규칙들을 각각 독립적으로 보면 다소 엄격한 규칙으로 보일 수 있다.
하지만 서로 연결하면 목적이 명확해진다.

``` text
                   외부 세계
                      │
                      ↓
                System Boundary
                      │
          ┌───────────┴───────────┐
          │                       │
    데이터 Validation         외부 예외 처리
          │                       │
          └───────────┬───────────┘
                      ↓
                검증된 상태만 통과
                      ↓
                   내부 코드
                      │
          ┌───────────┴───────────┐
          │                       │
       Null 최소화             명확한 계약
          │                       │
          └───────────┬───────────┘
                      ↓
                 Debug.Assert
                      │
                      ↓
             내부 계약 위반 조기 발견
                      │
                      ↓
                   핵심 로직
```

각 규칙의 역할을 요약하면 다음과 같다.

- **Null 관리**  
  → 값이 가질 수 있는 불확실한 상태를 줄인다.
- **Boundary Validation**  
  → 잘못된 외부 데이터가 내부로 들어오는 것을 막는다.
- **Boundary Exception Handling**  
  → 프로그램이 통제할 수 없는 외부 실패를 정해진 위치에서 처리한다.
- **Debug.Assert**  
  → 내부 계약이 깨진 순간 개발 단계에서 즉시 드러낸다.
- **내부 예외를 버그로 취급**  
  → 잘못된 상태를 복구하는 척하며 숨기지 않고 실제 원인을 제거한다.

결국 모든 원칙은 하나의 목표를 가진다.

> **프로그램 내부에서 고려해야 하는 불확실한 상태를 최대한 줄이는 것**

------------------------------------------------------------------------

## 8. 왜 이것이 실제 SW 품질 향상으로 이어지는가

실제 SW 버그는 단순한 오타 때문에만 발생하지 않는다. 상당수는 개발자가
암묵적으로 가지고 있던 가정이 깨질 때 발생한다.

예를 들면:

- "이 값은 `null`이 아니겠지."
- "여기까지 잘못된 데이터가 들어오지는 않겠지."
- "이 객체는 이미 초기화되어 있겠지."
- "이 enum 값은 여기 들어올 일이 없겠지."
- "이 인덱스는 항상 범위 안이겠지."
- "이 함수가 호출될 때 장비는 연결되어 있겠지."

이러한 가정이 코드 어디에도 표현되어 있지 않으면 가정이 깨졌을 때 문제를
빠르게 발견하기 어렵다.

본 표준은 이러한 가정을 가능한 한 코드에 표현한다.

``` csharp
Debug.Assert(mDevice != null);

User? user = GetUserOrNull(_userID);

if (!IsValidPacket(_packet))
{
    return;
}

default:
    Debug.Fail("unknown type");
    break;
```

즉:

``` text
개발자의 머릿속 가정
        ↓
    코드의 계약
        ↓
  검증 가능한 조건
```

으로 바꾸는 것이다.

SW 품질 향상에서 중요한 것은 단순히 개발자에게 "실수하지 않도록
주의한다"라고 요구하는 것이 아니다. 사람은 결국 실수할 수 있다.

더 좋은 접근은 다음과 같다.

> **실수하더라도 가능한 한 빠르고 원인에 가까운 위치에서 발견되는 구조를
> 만든다.**

------------------------------------------------------------------------

## 9. 내부에서 방어 코드를 많이 작성하는 것이 항상 안전한 것은 아니다

일반적으로 다음과 같은 코드는 안전해 보인다.

``` csharp
private void UpdateDevice()
{
    if (mDevice == null)
    {
        return;
    }

    if (!mDevice.IsConnected)
    {
        return;
    }

    ...
}
```

하지만 설계상 `UpdateDevice()`가 호출될 때 `mDevice`는 반드시 초기화되어
있고 연결도 완료되어 있어야 한다면 이야기가 다르다.

이 경우:

``` csharp
private void UpdateDevice()
{
    Debug.Assert(mDevice != null);
    Debug.Assert(mDevice.IsConnected);

    ...
}
```

가 더 적절할 수 있다.

첫 번째 방식에서는 잘못된 상태가 발생해도 프로그램이 조용히 넘어간다.
결과적으로 사용자에게는 단순히 "동작하지 않음"으로 나타날 수 있다.

두 번째 방식에서는 개발 과정에서 "UpdateDevice가 잘못된 상태에서
호출됨"이라는 사실을 바로 확인할 수 있다.

즉 방어 코드를 많이 작성하는 것이 항상 품질을 높이는 것은 아니다.
**복구해야 하는 오류와 고쳐야 하는 버그를 구분하는 것이 더 중요하다.**

``` text
복구 가능한 외부 오류
→ Validation / Exception Handling

발생해서는 안 되는 내부 오류
→ Assert / Debug.Fail / 버그 수정
```

------------------------------------------------------------------------

## 10. 명시적인 코드가 품질 향상에 도움이 되는 이유

본 표준은 `var`, `??`, using declaration, target-typed `new()` 등 일부
축약 문법을 제한하고, 여러 경우에 명시적인 코드를 선호한다. 원본
표준에서도 `??`를 금지하고, using declaration 대신 범위가 드러나는
using문을 사용하며, `new()` 대신 자료형을 명시하도록 규정하고 있다.

목적은 최신 문법 자체를 거부하는 것이 아니다. **코드의 작성량보다 읽을
때 필요한 추론의 양을 줄이는 것이 목적**이다.

예를 들어:

``` csharp
Device device;

if (mCachedDevice != null)
{
    device = mCachedDevice;
}
else
{
    device = CreateDevice();
}
```

는 다음보다 길다.

``` csharp
Device device = mCachedDevice ?? CreateDevice();
```

그러나 첫 번째 코드는 제어 흐름이 구조적으로 드러난다. 특히 디버깅
과정에서:

``` text
null 검사
    ↓
어느 branch가 실행됐는지 확인
    ↓
CreateDevice 호출 여부 확인
```

을 한 줄씩 따라가기 쉽다.

이러한 명시성은 코드 작성 당시보다 몇 개월 또는 몇 년 뒤 장애를 분석할
때 더 큰 가치를 가진다.

------------------------------------------------------------------------

## 11. 장기적인 품질 향상 효과

본 표준을 적용하면 단기적으로는 코드가 다소 길어지고 개발자가 확인해야
할 규칙도 증가할 수 있다. 하지만 SW의 전체 비용은 최초 구현 시간만으로
결정되지 않는다.

실제 유지보수에서는 다음 비용이 지속적으로 발생한다.

- 코드 이해
- 기능 수정
- 디버깅
- 장애 분석
- 타 개발자가 작성한 코드 파악
- Regression 원인 분석
- 신규 개발자 인수인계
- 과거 코드 재확인

특히 장기간 유지보수하는 SW에서는 코드를 작성하는 횟수보다 읽는 횟수가
훨씬 많다.

따라서 작성 시 약간의 비용을 추가하더라도 다음을 할 수 있다면 전체 SW
생명주기 비용은 오히려 낮아질 수 있다.

- 계약을 명시하고
- 상태를 단순화하고
- 오류 발생 영역을 한정하고
- 잘못된 상태를 조기에 발견

기대 효과는 다음과 같다.

- Null 관련 런타임 오류 감소
- 잘못된 외부 데이터의 내부 전파 감소
- 통신 및 외부 시스템 오류 처리 방식 통일
- 내부 오류를 조용히 무시하는 코드 감소
- 잘못된 내부 상태의 조기 발견
- 장애 원인과 오류 발생 위치의 거리 감소
- 디버깅 시간 단축
- 함수와 모듈 간 계약 명확화
- 코드 리뷰 시 판단 기준 통일
- 코드 인수인계 비용 감소
- 장기간 유지보수 시 해석 차이 감소

------------------------------------------------------------------------

## 12. 품질 향상을 위한 향후 적용 방향

본 코딩 표준 자체만으로 SW 품질이 자동으로 보장되는 것은 아니다. 코딩
표준은 SW 품질의 기본 바닥선을 형성하는 역할을 한다.

따라서 우선 코딩 표준을 안정적으로 정착시킨 후, 다음 품질 활동을
순차적으로 결합하는 것이 효과적이다.

``` text
1단계
코딩 표준 정착
    ↓
2단계
.editorconfig 및 Analyzer 활용
    ↓
3단계
코드 리뷰 기준 통일
    ↓
4단계
Unit Test / Integration Test 확대
    ↓
5단계
Issue / Pull Request 기반 변경 관리
    ↓
6단계
Regression Test 축적
```

특히 버그 수정 시에는 가능하다면 해당 버그가 다시 발생하지 않는지
확인하는 테스트를 추가한다.

그렇게 하면:

``` text
버그 발생
    ↓
원인 분석
    ↓
코드 수정
    ↓
재현 테스트 추가
    ↓
이후 동일 버그 재발 방지
```

의 구조를 만들 수 있다.

------------------------------------------------------------------------

## 13. 결론

본 코딩 표준에서 Null 관리, Boundary Validation, 예외 처리, Assert
사용을 강조하는 이유는 단순히 엄격한 코드를 작성하기 위해서가 아니다.

핵심 철학은 다음과 같다.

> **외부의 잘못된 상태와 실패는 경계에서 검증하고 처리한다. 경계를
> 통과한 내부에서는 명확한 계약을 신뢰한다. 그 계약이 깨지는 것은
> 정상적인 오류가 아니라 버그로 보고, Assert 등을 통해 최대한 빠르고
> 원인에 가까운 위치에서 발견하여 수정한다.**

이를 조금 더 단순하게 표현하면 다음과 같다.

``` text
외부는 의심한다.
    ↓
경계에서 검사하고 처리한다.
    ↓
내부는 검증된 상태만 사용한다.
    ↓
내부 계약 위반은 버그다.
    ↓
Assert로 빠르게 발견한다.
    ↓
숨기지 않고 원인을 수정한다.
```

따라서 이 표준이 추구하는 품질 향상은 **모든 오류를 방어 코드로 덮어
프로그램을 계속 실행시키는 것**이 아니라, **정상적으로 발생할 수 있는
외부 실패와 발생해서는 안 되는 내부 버그를 명확하게 구분하는 것**에
있다.

결국 목표는 버그가 절대 발생하지 않는 프로그램을 만드는 것이 아니다.
사람이 개발하는 이상 버그는 발생할 수 있다.

대신 목표는:

> **버그가 발생하기 어렵고, 발생하더라도 숨지 않으며, 최대한 빠르게
> 발견되고, 실제 원인을 쉽게 추적하여 수정할 수 있는 SW 구조를 만드는
> 것**

이다.

이러한 구조가 장기적으로 SW의 안정성, 유지보수성, 디버깅 효율과 개발팀
전체의 코드 품질을 높이는 기반이 된다.
